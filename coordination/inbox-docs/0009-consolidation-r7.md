## Part A — Core blending (D7)

`BlendBuilder1D` (Core) now:
1. **Selectable degree** (`int? blendDegree`, 3/5/7/9, others → `ArgumentException`). **Default rule: the degree of the neighbours if they agree, 9 otherwise** (`DefaultBlendDegree`, constant `MixedNeighbourDegree = 9`). Reason: a blend between two cubics should be a cubic (no higher derivatives to match); with different degrees the richest reference degree is the safe choice.
2. **Limits**: new `KinematicLimits? limits` argument. Prescribed `blendDuration` → kept and only verified; none and limits active → `ShortestFeasibleDuration.Find ?? inherited`; no limits → inherited duration (sum of the removed portions, floor 0.01 s as before). The blend is verified with `VerifyLimits`; failures: `KinematicLimitsViolatedException` ("The blend (duration … s) violates …") or `DurationSearchFailedException` whose message starts with "The blend:". Both builder entry points and `TrajectoryBuilder1D.AddBlendBetween` take the new optional arguments.
3. **Validation**: an absolute position the neighbour never reaches → `ArgumentException` ("… position 5 is outside the segment, which covers [0, 2]"); the range is the segment's true position range (`ExtremaAnalyzer.PositionExtrema`), so a segment that overshoots is handled; an empty window (nothing removed) → `ArgumentException("Empty blend window …")`; the pair method also rejects a window that removes a whole neighbour. The clamp of the normalized parameter to [0.001, 0.999] for absolute positions stays (public constants `TauMin`/`TauMax`).
4. **Position → parameter** moved into the Core as the public `TauForPosition`. It replaces both old Newton copies (Core and App) with a scan of 400 intervals plus bisection, so it no longer depends on the segment being monotone or on a starting guess; if the position is reached several times the **first** crossing is taken (documented; open question 1).

Tests changed because behaviour changed (and nothing else weakened): in `BlendBuilderTests`, `Today_PositionOutsideTheSegmentIsClampedNotRejected` → `PositionOutsideTheSegment_IsRejected`; `Today_EmptyWindow_IsNotRejected` → `EmptyWindow_IsRejected`; `Today_BlendDegreeIsNineByDefault` → `DefaultBlendDegree_IsTheDegreeOfTheNeighboursWhenTheyAgree`; `Today_InheritedDurationHasAFloor…` kept, but its input changed from the now-empty window (τ = 1, 0) to a tiny one (0.9999, 0.0001). `Today_AbsolutePositionTauIsClampedAwayFromTheEndpoints` is unchanged and passes. New file `BlendBuilderLimitsAndDegreeTests.cs` (25 cases): degree selection and default rule, degree-5 blend between degree-5 neighbours (continuity up to acceleration), each limit binding in turn (v, a, j, s: duration = `ShortestFeasibleDuration`, F ≈ 0, `VerifyLimits`), whole blended trajectory within limits, prescribed duration kept/violating, infeasible limits naming the blend, `TauForPosition` (crossing, clamp, non-monotone segment), absolute vs τ pair, whole-neighbour removal rejected.

## Part B — App consolidation (D11, D15)

**Moved to the Core**: `SegmentFactory1D.Build` (duration choice for an ordinary segment: prescribed → verified; limits → shortest feasible; otherwise fallback 1.0 s; this was `BuildPolynomialSegment` + `ValidateSegmentAgainstLimits` in the App); `Trajectory1D.Sample(count, maxOrder)` returning `TrajectorySamples` (the App's sampler and per-order evaluation loop); `KinematicLimits.MostRestrictive` and `HasAnyLimit` (the App's `HasAnyKinematicLimit`); `BlendBuilder1D.TauForPosition` (the App's copy of the Newton search).
**Removed from the App**: its blend point search, limit validation, duration choice for plain segments, sampling, the `ShortestDurationOrExplain`/`FindDurationOrExplain` helpers, the default-duration constant, the order `switch` over `ExtremaAnalyzer.*Extrema` (now `FindExtrema(segment, order)`), and the constant `9` for the blend degree.
**What remains in `PrototypeTrajectoryService`, and why** (acceptance criterion): parsing of the text fields (`ParseRequiredDouble`, `ParsePositiveDouble`: UI input); building `State1D` and `KinematicLimits` from the rows, with zero-fill of derivative orders the chosen degree does not use (depends on which fields the UI offers: `SupportsAcceleration` …); the labelling of pieces ("Segment 1", "Blend 1-2", "… Entry") and flattening them for the report; the two report tables (rows of extrema and coefficients, `T [s]` first); the series for the plots (names "Position" … "Snap"); the rule "blend needs both values / not on constant-velocity segments" (a UI-model restriction); one adapter `CallCore` turning Core failures (`DurationSearchFailedException`, `KinematicLimitsViolatedException`, `ArgumentException`) into one `InvalidOperationException` whose message names the segment or blend, which `MainWindow` shows. `MainWindow` itself contains only `Math.Clamp` for indexes and the cursor time, and calls `PositionAt`/`DerivativeAt`, which are Core functions of the trajectory.
**Blend limits**: the blend takes the **most restrictive** limit of each kind of its two neighbours (new rule in the App: the UI has no blend limit fields); this is a choice for you to confirm (open question 2).
**D15**: `ComputeDuration` removed from `IDurationStrategy1D` and from `UserSpecifiedDuration`/`AutoDerivedProportionalDuration`; the enum `DurationMode` and the `Mode` properties (read by nobody) are gone too. The interface now has the single member `ComputeDurations(waypoints, degree)`. Behaviour of the three strategies is unchanged, with one structural consequence: **`ConstraintAwareDuration` no longer implements the interface** (it never could size a waypoint sequence; its former `ComputeDurations` just threw `NotSupportedException`). It keeps its shortest-feasible behaviour as `ComputeDuration(degree, start, end)` plus the fallback duration, so passing it to the pass-through builder is now a compile error instead of a run-time one.

**Tests for the service (B.4): yes, it is possible without a window.** The service is a plain class, and a test project that targets `net8.0-windows` with `UseWPF` can reference the App project (I used this for the throw-away console checks of 0006–0008). I therefore added **`src/TrajectoryPlanner.App.Tests`** (xUnit, 26 tests, added to the solution file) rather than moving more code to the Core, and kept the rule "`Core.Tests` tests Core only". It covers: default/auto/prescribed durations, coefficient labels `T [s]`, `c0…`, shortest feasible duration (315/128; loose limit 315/1280; degree 7 with a_max = 3), prescribed duration violating a limit, impossible limits, zero-length segment, non-numeric input, extrema rows, result functions; constant velocity (Rule 2 default, Rule 3 total split 8/4/8, total ≤ T_cv, a_max = 6 giving 13.0113 s, speed above v_max, minimum feasible total in the message, equal stretch positions); blending (degree 9 durations, degree 5 blend polynomial, limit shortens the blend and stays at the limit, position outside naming the blend, both values required, not on constant-velocity segments); two segments without blend. Cost: the project is Windows-only and `dotnet test` of the whole solution needs the WPF workload, like the App itself.

## For the author (educational)

- **"Thin layer over the Core."** The service answers only: *what did the user type, which Core function turns that into a trajectory, and how do I display the result?* Logic belongs in the Core when it would give the same answer without any window: deciding a duration, checking limits, finding where a position occurs on a polynomial, sampling a trajectory. A quick test: could a script, a different UI or a unit test need the same decision? Then it must not live in the UI, otherwise each client re-implements it (the App had its own Newton search that already differed in details from the Core's copy, and its own duration rules that diverged from the Core's, see D11). What stays in the App is text parsing, labels and table layout.
- **Why the blend needs a shortest feasible duration like any other segment.** The blend is just a polynomial between two states taken from the neighbours; its duration is the free parameter that decides how violent it is. Inheriting "whatever time the neighbours gave up" ignores the limits entirely, and a blend between two opposite velocities can need far more acceleration than either neighbour. With limits, the same rule as everywhere applies: the shortest duration that stays inside them. Note the consequence in the table: with v_max = 8 the blend became **much shorter** (0.64 → 0.10 s) because the old duration was needlessly gentle; the limit is now reached exactly (peak v = 8). If you prefer the gentler inherited duration whenever it is feasible, that is a different rule (open question 3).
- **What the user sees differently.** A blend position that is not on the segment now produces an error that names the blend and the range the segment covers, instead of a silently shifted blend; an empty window and an unsupported degree are errors as well; limit violations of a blend are reported like those of segments.
- **Odd things found in the App while moving code.** (1) The old App position search returned 0.5 silently when a segment's start and end positions coincided (flat segment) and clamped the first guess to [0.01, 0.99] while the Core used [0.001, 0.999]: two behaviours for the same thing. (2) Blend limits were never checked (the blend ignored the segments' limits). (3) The blend degree was hard-coded to 9 regardless of the neighbours. (4) **`double.TryParse(value, …)` without a culture**: on a PC with Italian regional settings a decimal point may be read as a thousands separator or rejected; this has not been exercised here (the tests run with the machine's settings). It is a UI-input concern left untouched; worth a decision (invariant or current culture). (5) `MainWindow` compiles an unused `SegmentNumber` path for blends only through labels; nothing wrong, just noted.

## Open questions

1. A position reached more than once by an overshooting segment: first crossing (current) or the crossing closest to the join? For the preceding segment the second is arguably the natural one.
2. Blend limits = most restrictive of the two neighbours (current). Alternatives: limits of the preceding segment only, or explicit blend limits in the UI (R10).
3. Blend duration with limits: shortest feasible (current, by your decision for ordinary segments) or "inherited if feasible, else shortest"?
4. Delete the unused public members and the `BoundaryConditions` module listed above, or keep them for the 3D work (R9)?
5. Culture of number parsing in the UI (see odd thing 4).
